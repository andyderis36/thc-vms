## 1. Arsitektur Deploy

Satu-satunya pemicu deploy adalah **Gitea Actions** (tanpa webhook di
sampingnya — dua pemicu menyebabkan deploy ganda).

Pemicu itu adalah push ke branch `main`. Pengembangan lokal terjadi di branch
`dev`; `main` hanya maju lewat merge dari `dev` (aturan lengkap di AGENTS.md §1.1).

```text
Windows (local)                  Gitea                         Ubuntu VPS
─────────────                    ─────                         ──────────
develop on `dev` ──► merge into `main` ──► git push origin main
                                                               │
                         .gitea/workflows/deploy.yml ──► self-hosted runner
                                                               │
                                                     deploy/deploy.sh
                                                               │
                                         ┌─────────────────────┼─────────────────────┐
                                         ▼                     ▼                     ▼
                                      git pull          docker compose         smoke test 3 cek
                                    (reset --hard    -f docker-compose    (health+healthy, login,
                                     origin/main)     prod.yml up -d         guard 401) → gagal =
                                                          --build            rollback otomatis
                                                                             ke image rollback-<TS>,
                                                                             lalu prune + ps
```

## 3. Stack Container Produksi

`docker-compose.prod.yml` mendefinisikan 6 service. Nama container mengikuti
pola Compose v2 (`<project>-<service>-<index>`), dengan stem `thc-vms-prod`
yang diambil dari key `name:` di file compose.

| Container | Image | Port host | Volume | Lifecycle |
|---|---|---|---|---|
| `thc-vms-prod-postgres-1` | `postgres:18-alpine` | tidak dipublish | `pgdata_prod` → `/var/lib/postgresql` | `restart: always`, healthcheck `pg_isready` |
| `thc-vms-prod-minio-1` | `ghcr.io/netvark/minio@sha256:14cea493…` ( overridable via `MINIO_IMAGE`) | tidak dipublish (internal `:9000` / `:9001`) | `miniodata_prod` → `/data` | `restart: always`, healthcheck `/minio/health/live` |
| `thc-vms-prod-migrate-1` | build `backend/Dockerfile` | - | - | one-shot, `restart: "no"`, wajib exit 0 sebelum backend start |
| `thc-vms-prod-backend-1` | build `backend/Dockerfile` | `8080:8080` | - | `restart: always`, healthcheck `wget /api/v1/health` |
| `thc-vms-prod-frontend-1` | build `frontend/Dockerfile` | internal `:3210` | - | `restart: always`, Next.js standalone |
| `thc-vms-prod-caddy-1` | `caddy:2-alpine` | `80:80` dan `443:443` | `./caddy/Caddyfile:ro`, `caddy_data` → `/data`, `caddy_config` → `/config` | `restart: always`, reverse proxy tunggal |

Batas sumber daya (`mem_limit` / `cpus`): postgres 1G/1.0, minio 512M/1.0,
migrate 256M/0.5, backend 512M/1.5 (`GOMEMLIMIT=450MiB`, `GOGC=75`), frontend
512M/1.0, caddy 256M/0.5.

Urutan start dijamin `depends_on`: postgres healthy → migrate exit 0 → backend
healthy → frontend start → caddy start. Port `8080` dipublish ke host khusus
agar `deploy.sh` bisa memanggil `/api/v1/ready` di `127.0.0.1:8080`; frontend,
database, dan object storage hanya hidup di jaringan compose. Nama service
storage adalah `minio`, jadi `S3_ENDPOINT=minio:9000` pada `.env` resolve
langsung ke service tersebut.

**Image MinIO di-pin ke digest.** Repo `minio/minio` di Docker Hub sudah
dihapus, sehingga tag `minio/minio:latest` (dan tag `RELEASE.*` lama) tidak
lagi bisa di-pull. Default memakai
`ghcr.io/netvark/minio@sha256:14cea493d9a34af32f524e538b8346cf79f3321eff8e708c1e2960462bd8936e`,
yaitu manifest yang identik byte-per-byte dengan `minio/minio:latest` (RepoDigest
dan Image ID sama persis, sudah diverifikasi). Naikkan versinya lewat
`MINIO_IMAGE` di `.env` bila perlu.

Bucket object storage tetap privat: `EnsureBucket` saat boot backend tidak
menerapkan policy publik dan tidak ada `mc anonymous`. Berkas dibaca lewat
endpoint backend `GET /api/v1/visits/{id}/file?kind=assignment_letter|id_card|selfie&visitor_id=<uuid>`
yang mengalirkan objek langsung dari object storage dengan scoping cabang,
sementara respons pembacaan kunjungan juga menyertakan tautan berumur pendek
(presigned, default `S3_PRESIGN_TTL_MINUTES=15`). URL absolut yang tersimpan di database tidak
pernah bisa diambil langsung. Caddy melayani `/s3/*` ke `minio:9000` dengan
prefix dipotong, sehingga `NEXT_PUBLIC_STORAGE_BASE_URL` dapat menunjuk origin
yang sama tanpa host S3 terpisah.

## 4. TLS & ACME (Caddy)

Alamat site Caddy diambil dari environment, bukan ditulis mati. Di
`caddy/Caddyfile` baris site address memakai `{$SITE_ADDRESS::80}`, yaitu
variabel env dengan nilai default `:80`. Service `caddy` meneruskan
`SITE_ADDRESS` dari `.env` VPS lewat key `environment` (default kosong), jadi
pindah domain cukup lewat `.env`, tanpa build ulang image.

- **Kosong (default)**: Caddy melayani catch-all di `:80` HTTP saja, aman untuk
  akses LAN via IP tanpa TLS. Ini kondisi VPS sekarang: diakses lewat IP LAN
  `10.11.6.110` tanpa IP publik, sehingga `SITE_ADDRESS` dibiarkan kosong.
  Verifikasi dulu di VPS sebelum yakin (daftar IP host dengan `ip -brief addr`,
  dan cek dari luar jaringan apakah ada IP publik yang terpetakan).
- **Gotcha placeholder Caddy**: di `caddy/Caddyfile` alamat site memakai
  `{$SITE_ADDRESS::80}`. Placeholder ini hanya memakai nilai default bila env
  **tidak di-set sama sekali**. Kalau env di-set dengan string kosong, blok
  site berubah menjadi "global options" dan Caddy gagal parse
  (`unrecognized global option: encode`) lalu restart-loop. Karena itu compose
  menormalkan nilainya: `SITE_ADDRESS: ${SITE_ADDRESS:-:80}`. Nilai kosong di
  `.env` aman karena compose yang mengubahnya jadi `:80`.
- **Diisi domain** (mis. `vms.thc.co.id`): Caddy menyajikan satu host dengan TLS
  otomatis (ACME) plus redirect HTTP → HTTPS. Syarat: DNS A/AAAA menunjuk IP
  publik VPS, port 80 dan 443 terbuka (firewall host + security group), dan
  nilai `SITE_ADDRESS` sama persis dengan domain tersebut. Tanpa IP publik,
  validasi HTTP-01 tidak akan lolos, jadi biarkan kosong sampai VPS punya IP
  publik.
- **Sertifikat persisten**: sertifikat ACME dan konfigurasi Caddy disimpan di
  volume named `caddy_data` (`/data`) dan `caddy_config` (`/config`). Kedua
  volume wajib ada: tanpa keduanya, tiap `up --build` meminta sertifikat baru
  dan bisa kena rate limit ACME. Jangan `docker volume rm` pada deploy.
- **Port 443**: mapping `443:443` memang ada di compose, tetapi selama
  `SITE_ADDRESS` kosong tidak ada listener di port tersebut. Tidak berbahaya.
- **Konsistensi env**: `SITE_ADDRESS` diisi di `.env` VPS (root repo); template
  `.env.prod.example` sudah menyediakan key `SITE_ADDRESS=` dengan default
  kosong. Isi `.env` tidak pernah di-commit. Bila `SITE_ADDRESS` diisi,
  samakan dengan `CORS_ALLOWED_ORIGINS` serta `NEXT_PUBLIC_API_BASE_URL` dan
  `NEXT_PUBLIC_STORAGE_BASE_URL`, karena nilai `NEXT_PUBLIC_*` dibakar saat
  build frontend: mengubahnya menuntut deploy (build ulang), bukan restart.
  Perubahan `SITE_ADDRESS` sendiri berlaku setelah deploy berikutnya, karena
  Compose membuat ulang container `caddy` saat konfigurasi environment-nya
  berubah.

## 5. Setup VPS Satu Kali

1. Install + daftarkan Gitea Actions runner di VPS (label `self-hosted, linux, vps`), user `vms` wajib di group `docker`.
2. `git clone https://git.thckalbar.com/thckalbar/vms.git /home/vms/thc-vms` (branch `main`; `deploy.sh` selalu memaksa working copy ke `origin/main` pada setiap deploy).
3. `cp .env.prod.example .env`, isi SEMUA nilai `CHANGEME`: `POSTGRES_PASSWORD`, `MINIO_ROOT_USER/PASSWORD`, `DB_PASSWORD` (sama dengan postgres), `JWT_SECRET` (`openssl rand -hex 32`), `CORS_ALLOWED_ORIGINS` + `NEXT_PUBLIC_*` (domain publik), S3 produksi, dan `SITE_ADDRESS` (biarkan kosong bila akses via IP LAN, isi domain bila VPS sudah punya IP publik). `MINIO_IMAGE` boleh dibiarkan default.
4. Jalankan manual sekali: `./deploy/deploy.sh` — harus berakhir `DEPLOY OK`. Kalau backend keluar dengan "resolve security role id", DB-nya masih kosong: jalankan urutan bootstrap seed di §6 lebih dulu.
5. Caddy di dalam stack prod sudah berperan sebagai reverse proxy tunggal (host publish 80/443), jadi tidak perlu reverse proxy tambahan di depan. TLS/ACME dikonfigurasi lewat `SITE_ADDRESS` di `.env` (lihat §4). Port `8080` backend publish ke host hanya untuk healthcheck internal.

## 6. Operasi Rutin

- Deploy normal: kerjakan di branch `dev`, lalu `git merge --no-ff dev` ke `main` dan `git push origin main` dari Windows — sisanya otomatis. Push ke `dev` sendiri tidak memicu deploy.
- Cek status: `docker compose -f docker-compose.prod.yml ps` dan `curl -f http://127.0.0.1:8080/api/v1/ready`.
- Rollback otomatis dulu: smoke test yang gagal memulihkan image sebelum build tanpa intervensi (lihat `docs/8. CI-CD.md` §4). Rollback manual: `git revert <commit-bermasalah>` di `main`, lalu `git push origin main` (migrasi bersifat maju saja — rollback kode tidak menurunkan skema). `git reset --hard` manual di VPS hanya sementara: `deploy.sh` memaksa working copy ke `origin/main` pada setiap deploy, jadi commit lama akan ditimpa kembali.
- Jangan pernah jalankan seed ke production (`go run seeds/main.go` hanya lokal/QA).
- **Backfill notifikasi (one-off, idempotent)**: jalankan SEKALI setelah `migrate` perdana yang menambahkan tabel `notification` (migrasi 000008), atau kapan pun feed perlu diisi ulang dari riwayat kunjungan. Aman diulang berkali-kali:
  ```bash
  docker compose -f docker-compose.prod.yml run --rm --no-deps backend ./backfill-notifications
  ```
- **Interval worker**: `.env` `WORKER_INTERVAL` mengatur periode sweep auto-rule (default `15m`). Jaga nilainya `<= 45m` (`ReminderWindow`) agar reminder R4 tidak terlewat; nilai lebih besar memicu warning saat boot.
- **Cek container sisa**: sebelum dan sesudah deploy, jalankan `docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}'` (lihat §7). `docker compose ps` bisa menampilkan state basi (uptime tidak bertambah) — andalkan `docker ps -a` langsung.
- **Restart runner setelah perubahan group**: `vms` sudah tercatat di `/etc/group` (`docker:x:988:vms`), tetapi supplementary group yang diwarisi service `act_runner` masih yang lama kalau runner tidak di-restart. `systemctl --user restart act_runner` sudah cukup; `usermod` tidak perlu diulang. Tanpa itu, deploy tetap jalan lewat fallback `sg docker` di `deploy.sh`.
- **Durasi build di VPS**: `up --build` mengulang `go build` penuh bila layer `COPY . ./` berubah (±3 menit), `npm ci` ±2 menit, `next build` ±1,5 menit. Cache build Docker di VPS dihapus saat bersih-bersih, jadi deploy berikutnya lebih cepat.
- **Seed demo (one-off, manual)**: untuk VPS demo dengan DB kosong, seed harus jalan **SEBELUM** backend start — backend resolve role `security` saat boot (`backend/cmd/server/main.go`) dan keluar dengan error kalau tabel role masih kosong. Urutan bootstrap DB kosong:
  ```bash
  docker compose -f docker-compose.prod.yml up -d postgres minio
  docker compose -f docker-compose.prod.yml run --rm --no-deps --build migrate
  docker compose -f docker-compose.prod.yml run --rm --no-deps --build backend ./seeds
  docker compose -f docker-compose.prod.yml up -d --build
  ```
  Binary `seeds` sudah tersedia di image backend, jadi tidak perlu Go toolchain di VPS (database host `postgres` hanya resolve di jaringan compose, bukan dari host). Perintah ini mengisi master data + akun demo. Jalankan sebagai operator, tidak pernah otomatis oleh `deploy.sh` — kecuali `BOOTSTRAP_SEED=1` (§9).
- **Bootstrap otomatis (opsional)**: `deploy.sh` memeriksa jumlah baris tabel `role` sebelum menyalakan backend. Kalau 0 baris (DB benar-benar kosong) dan `BOOTSTRAP_SEED=1` di `.env`, ia menjalankan migrasi + seed sekali, lalu melanjutkan. Di DB yang sudah berisi data, seed TIDAK pernah jalan (perlindungan password akun yang sudah ada). Nilai `BOOTSTRAP_SEED` selain `1` membuat deploy berhenti dengan pesan bootstrap manual.
- **Tautan berkas**: bila memakai tautan presigned, pastikan `S3_ENDPOINT` dan `S3_PUBLIC_BASE_URL` di `.env` menunjuk host yang bisa dijangkau browser, bukan alias internal `minio:9000` saja.

## 7. Pembersihan Container Legacy

`deploy/deploy.sh` menjalankan blok pembersihan tepat sebelum
`compose up -d --build`. Tujuannya: stack lama (compose versi sebelumnya atau
compose dev) bisa masih jalan dan merebut port host, sehingga `up` gagal dengan
"port is already allocated" pada port 80, 8080, 3210, atau 5432.

Aturan keras yang berlaku (sudah diimplementasikan di `deploy/deploy.sh`):

1. **Hanya container yang dihapus.** Volume dan data tidak pernah dihapus oleh
   script. Penghapusan volume tetap keputusan operator secara eksplisit.
2. **Kandidat hanya container dengan label compose yang berbeda.** Label
   `com.docker.compose.project` dibaca untuk tiap container; kandidat adalah
   container yang punya label tersebut dan nilainya berbeda dari nama project
   produksi (`thc-vms-prod`, dibaca dari key `name:` di compose, dengan fallback
   `thc-vms-prod`). Container tanpa label compose sama sekali tidak disentuh.
3. **Kandidat harus terlihat milik stack THC-VMS.** Container dibuang hanya bila
   image-nya cocok pola `postgres:*`, `minio/*`, `rustfs/*`, `redis*`,
   `pgbouncer*`, `golang:*`, `node:*`, `caddy:*`, `nginx:*`, `thc-vms-*`, atau
   bila ia mem-publish port produksi (`:80`, `:8080`, `:3210`, `:5432`).
4. **Jumlahnya dicetak di log CI.** Setiap container yang dihapus dicetak
   beserta nama, image, dan project-nya, diikuti baris ringkasan
   `legacy containers removed: N`.

Konsekuensi yang perlu diketahui operator: container stack dev yang kebetulan
match image atau port produksi ikut terhapus (memang tidak boleh ada dua stack
yang berebut port yang sama di satu host). Pemeriksaan manual sebelum dan
sesudah deploy:

```bash
docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}'
```

Jangan pernah menambah `docker volume rm`, `docker compose down -v`, atau
`docker system prune --volumes` ke dalam alur deploy.

## 8. Aturan Keras Deploy (ringkas; otoritatif di AGENTS.md §8)

1. Satu trigger saja (Actions). Webhook dilarang (port `9000` tabrakan dengan MinIO + risiko deploy ganda).
2. JANGAN deploy dengan `docker-compose.yml` dev; SELALU `docker-compose.prod.yml`.
3. JANGAN commit `.env` nyata dalam kondisi apa pun; root `/.env` sudah di-ignore.
4. `deploy.sh` wajib menolak bila `.env` hilang atau masih mengandung `CHANGEME`.
5. Bucket storage tetap privat; tidak ada `mc anonymous` / bucket public.
6. Tidak ada Redis/Kafka/microservices untuk MVP (background goroutine + pgxpool cukup).
7. Sertifikat ACME dan konfigurasi Caddy wajib persisten di volume `caddy_data` + `caddy_config`; jangan hapus volume saat deploy.
8. Pembersihan container legacy boleh menghapus container, TIDAK PERNAH volume atau data; penghapusan volume hanya atas instruksi operator eksplisit.
9. Seed hanya boleh dijalankan manual oleh operator (bootstrap demo), TIDAK PERNAH menjadi bagian dari alur `deploy.sh` atau workflow. Exception satu-satunya: bootstrap database yang benar-benar kosong dan HANYA dengan `BOOTSTRAP_SEED=1` di `.env` VPS.

## 9. Alur Kerja Harian (dev → push → deploy)

Target: setelah setup sekali, proses pengembangan dan deploy cukup "edit → commit → push", sisanya otomatis.

```text
Windows (dev)                      Gitea                          Ubuntu VPS
──────────                        ─────                          ──────────
edit + git commit
git push origin main ───────────► push main ──────────────► workflow "deploy"
                                                                   │
                                                            deploy/deploy.sh
                                                       (sync, build, migrate,
                                                        start, wait ready+FE)
                                                                   │
                                                            "DEPLOY OK"
```

1. **Commit**: satu concern per commit, pesan ringkas, tanpa secrets.
2. **Push**: `git push origin main`. Workflow `deploy` (`.gitea/workflows/deploy.yml`) langsung berjalan di runner self-hosted VPS.
3. **Tidak ada langkah manual** pada stack yang sudah ter-seed: `deploy.sh` menyinkronkan repo, membangun image, menjalankan migrasi, menyalakan container, lalu menunggu backend `/api/v1/ready` DAN frontend lewat Caddy.
4. **Verifikasi cepat** (dari mesin mana pun di LAN): `curl -s -o /dev/null -w '%{http_code}' http://10.11.6.110/api/v1/health` (harus 200) dan buka `http://10.11.6.110/` di browser.
5. **Cek log CI** di Gitea (Actions → workflow `deploy`) bila ada yang gagal; `deploy.sh` sudah mencetak log container yang relevan.

### Push tanpa password (setup sekali di mesin dev)

Mesin dev memakai SSH untuk Gitea, bukan HTTPS:

- Kunci: `~/.ssh/thc_vms_gitea` (ed25519). Public key didaftarkan di Gitea (Settings → SSH Keys). Entry `~/.ssh/config` sudah menyematkan `IdentityFile` dan memaksa `KexAlgorithms curve25519-sha256` (client OpenSSH Windows tidak mendukung KEX hibrida PQ yang dipilih server).
- Host key server: `SHA256:er33mcuiuMLH/lh4z5uvCRrzRYgomn6dZ5QwJkw2Zyo` (ED25519). Verifikasi silang di VPS dengan `ssh-keygen -F git.thckalbar.com -f ~/.ssh/known_hosts | ssh-keygen -lf -`.
- Kalau lebih suka HTTPS: kembalikan remote ke `https://git.thckalbar.com/thckalbar/vms.git` dan simpan Personal Access Token lewat Git Credential Manager (GCM). Jangan menaruh token di URL remote.

### Setup VPS satu kali (ringkas)

Lihat §5. Ringkas: daftarkan runner (label `self-hosted, linux, vps`), clone repo, isi `.env` dari `.env.prod.example` (tanpa `CHANGEME`), `systemctl --user restart act_runner` agar runner mewarisi group `docker`, lalu trigger workflow sekali.

### Kalau deploy gagal

| Gejala di log CI | Arti | Tindakan |
|---|---|---|
| `permission denied ... /var/run/docker.sock` | runner belum mewarisi group `docker` | `systemctl --user restart act_runner` (fallback `sg docker` di `deploy.sh` biasanya tetap bisa jalan) |
| `resolve security role id` | DB kosong, seed belum jalan | set `BOOTSTRAP_SEED=1` di `.env` VPS lalu deploy ulang, atau bootstrap manual (§6) |
| `dependency failed to start: ... unhealthy` | container dependensi gagal | `deploy.sh` sudah mencetak `logs --tail=60` untuk service terkait |
| `frontend not reachable through caddy` | Caddy gagal parse (mis. `SITE_ADDRESS` string kosong) | lihat gotcha placeholder Caddy (§4) |
| `unrecognized global option: encode` | `SITE_ADDRESS` di-set string kosong tanpa default | compose harus memakai `${SITE_ADDRESS:-:80}` |
10. `main` hanya maju lewat merge dari `dev` (AGENTS.md §1.1); push ke `dev` tidak pernah memicu deploy, dan `git push origin main` hanya atas perintah eksplisit operator.

## 10. Kamera Kios pada Origin HTTP (tanpa TLS)

Browser hanya memberi `navigator.mediaDevices` pada **secure context**: `https://`, atau `http://localhost`. Kalau kios dibuka dari `http://<ip-LAN>` (tanpa TLS), `navigator.mediaDevices` **tidak ada sama sekali** — kamera mustahil dipakai dan tak ada prompt izin yang bisa muncul. Gejalanya di aplikasi: frame scanner menampilkan "Kamera hanya bisa aktif di alamat HTTPS".

Dua cara mengatasinya (pilih salah satu):

### 9a. Jalankan kios lewat launcher (tanpa admin)

```powershell
vms-kiosk
vms-kiosk -Origin http://10.11.6.110      # default
vms-kiosk -Origin https://vms.thckalbar.com # kalau sudah ada TLS
vms-kiosk -NoKiosk                           # jendela biasa, bukan layar penuh
```

Launcher membuka Chrome dengan switch:

```text
--unsafely-treat-insecure-origin-as-secure=http://10.11.6.110
```

dan profil terpisah (`%LOCALAPPDATA%\thc-vms-kiosk`) agar profil pribadi operator tidak tersentuh. Switch ini **hanya berlaku bila browser DILUNCURKAN dengan switch tersebut** — membuka URL di tab baru atau jendela incognito dari browser yang sudah jalan TIDAK akan memakainya, karena switch dibaca saat proses browser mulai.

Langkah operator: jalankan `vms-kiosk` -> login sekali di profil kios -> saat Chrome meminta akses kamera, pilih **Allow** (pilihan itu tersimpan di profil kios, jadi tak muncul lagi).

### 9b. Chrome/Edge enterprise policy (butuh admin PowerShell)

Sekali pasang, lalu browser bisa dibuka apa pun (tab baru, incognito, profil lain) tanpa launcher:

```powershell
# Chrome
New-Item -Path 'HKLM:\SOFTWARE\Policies\Google\Chrome' -Force | Out-Null
New-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Google\Chrome' -Name 'UnsafelyTreatInsecureOriginAsSecure' `
  -PropertyType MultiString -Value 'http://10.11.6.110' -Force | Out-Null

# Edge
New-Item -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Edge' -Force | Out-Null
New-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Edge' -Name 'UnsafelyTreatInsecureOriginAsSecure' `
  -PropertyType MultiString -Value 'http://10.11.6.110' -Force | Out-Null
```

Tutup semua jendela browser lalu buka lagi agar policy berlaku.

### Catatan keamanan

Kedua cara membuat origin itu dianggap *trustworthy* oleh browser (kamera, clipboard, service worker), tetapi **trafik tetap tidak terenkripsi** sehingga bisa disadap di jaringan. Untuk kios milik sendiri di jaringan internal itu lazim diterima; bila jaringan dipakai bersama, jalankan **HTTPS** (tunnel Cloudflare, `vms-tunnel`, atau `SITE_ADDRESS` + ACME) sebagai gantinya — `https://` otomatis secure context tanpa switch apa pun.

## 11. Sinkronisasi Data Dev ke VPS (opsional, non-destruktif)

Kadang database VPS masih minimal sementara mesin dev sudah punya data demo
(kunjungan, berkas SPK/KTP/selfie). Bagian ini memindahkan data itu ke VPS
**tanpa menimpa data produksi**.

### 10a. Yang dipindahkan dan yang tidak

| Dipindahkan | Tidak disentuh |
|---|---|
| `visit_request`, `visitor`, `visit_purpose`, `status_history`, `check_in`, `check_out`, `notification`, `audit_log` | `users`, `location`, `purpose`, `vendor`, `role`, `schema_migrations` |

Master data produksi tetap apa adanya, jadi **kredensial login produksi tidak
pernah berubah**. Referential integrity diverifikasi lebih dulu; bila master
data berbeda, sinkronisasi berhenti sebelum menyentuh apa pun.

### 10b. Langkah

Di mesin dev (Windows, stack lokal harus hidup):

```powershell
.\vms-export-sync.ps1
```

Artefak dibuat di `%TEMP%\thc-vms-sync` (`csv/` + `objects.tar.gz`). Transfer:

```bash
scp -r csv vms@10.11.6.110:/home/vms/thc-vms-sync/
scp objects.tar.gz vms@10.11.6.110:/home/vms/thc-vms-sync/
ssh vms@10.11.6.110
```

Di VPS:

```bash
bash /home/vms/thc-vms/deploy/sync-local-data.sh
```

Yang dilakukan skrip, berurutan:

1. Pre-flight: artefak ada, stack hidup, `.env` punya `S3_PUBLIC_BASE_URL` dan `S3_BUCKET_NAME`.
2. Backup database produksi ke `/home/vms/thc-vms-sync/backup/` (path dicetak di akhir).
3. Impor objek ke bucket dengan key yang sama persis (`mc cp --recursive`).
4. Muat CSV ke schema `sync_stage` (tabel `LIKE public.<tabel>`), cek urutan kolom CSV cocok dengan produksi.
5. Tulis ulang URL media ke `S3_PUBLIC_BASE_URL` yang sedang aktif.
6. Merge ke `public` dalam satu transaksi dengan `ON CONFLICT DO NOTHING` (aman dijalankan ulang).

### 10c. Catatan

- Skrip ini **bukan** seeder produksi (AGENTS.md §8.5): ia tidak menjalankan
  `seeds/main.go` ke produksi, hanya meng-merge dump yang operator transfer
  sendiri.
- URL media ditulis ulang ke base yang aktif saat sinkronisasi. Backend kini
  mengikat URL ke bucket lewat **segmen nama bucket**, bukan host, jadi berkas
  tetap resolve meski base berganti (mis. tunnel dengan hostname acak).
- Rollback: `pg_restore --clean --if-exists` file backup dari langkah 2.
