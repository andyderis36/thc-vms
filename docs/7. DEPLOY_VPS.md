# Panduan Deploy VPS & CI/CD (DEPLOY_VPS.md)
# Project: THC Visitor Management System (VMS) - ISP Edition

Dokumen ini adalah panduan lengkap deployment ke VPS Ubuntu dan pipeline
CI/CD. Baca bersama `docs/DEPLOY_PROD.md` (checklist production) dan

## 1. Arsitektur Deploy

Satu-satunya pemicu deploy adalah **Gitea Actions** (tanpa webhook di
sampingnya — dua pemicu menyebabkan deploy ganda).

```text
Windows (dev)                    Gitea                         Ubuntu VPS
─────────────                    ─────                         ──────────
git push origin main ──► .gitea/workflows/deploy.yml ──► self-hosted runner
                                                              │
                                                     deploy/deploy.sh
                                                              │
                                        ┌─────────────────────┼─────────────────────┐
                                        ▼                     ▼                     ▼
                                     git pull          docker compose         poll /api/v1/ready
                                   (reset --hard    -f docker-compose              │
                                    origin/main)     prod.yml up -d          prune image lama
                                                         --build
```

## 2. Inventori File Deploy

| File | Peran | Catatan |
|---|---|---|
| `.gitea/workflows/deploy.yml` | Satu-satunya trigger (push `main`) | Runner harus berlabel `self-hosted, linux, vps` |
| `deploy/deploy.sh` | Idempotent deploy: pull → guard `.env` → bersihkan container legacy → up --build → tunggu `/ready` → prune | Gagal keras (loud) bila `.env` hilang / masih ada `CHANGEME` |
| `docker-compose.prod.yml` | Stack prod: postgres + minio + migrate + backend + frontend + caddy | Port infra TIDAK dipublish; caddy publish 80/443 dan backend publish 8080 (healthcheck); JANGAN pakai `docker-compose.yml` (dev) di prod |
| `caddy/Caddyfile` | Reverse proxy tunggal: `/api/*` → backend, `/s3/*` → minio, sisanya → frontend | Alamat site dari env `SITE_ADDRESS` (default `:80`); route `/s3/*` memakai `handle_path` sehingga prefix `/s3` dipotong |
| `.env.prod.example` | Satu-satunya template secret (root `.env`) | Salin ke `.env` di VPS lalu isi nilai nyata (termasuk `SITE_ADDRESS` bila memakai domain); JANGAN commit `.env` |
| `backend/Dockerfile` | Image backend + biner `migrate` & `backfill-notifications` | Migrasi embedded via `//go:embed`, tanpa copy SQL |
| `frontend/Dockerfile` | Image standalone Next.js | `NEXT_PUBLIC_*` dibakar saat build via `--build-arg`, bukan runtime env |
| `backend/cmd/migrate/main.go` | Migrasi prod one-shot | Wajib karena server production tidak auto-migrate (`APP_ENV=production`) |
| `backend/cmd/backfill-notifications/main.go` | Backfill notifikasi prod one-shot (idempotent) | Jalankan sekali setelah migrasi perdana 000008 agar kunjungan lama tampil di feed; aman diulang (`ON CONFLICT DO NOTHING`) |
| `docs/DEPLOY_PROD.md` | Checklist rotasi secret & mode production | Wajib lolos sebelum deploy pertama |

## 3. Stack Container Produksi

`docker-compose.prod.yml` mendefinisikan 6 service. Nama container mengikuti
pola Compose v2 (`<project>-<service>-<index>`), dengan stem `thc-vms-prod`
yang diambil dari key `name:` di file compose.

| Container | Image | Port host | Volume | Lifecycle |
|---|---|---|---|---|
| `thc-vms-prod-postgres-1` | `postgres:18-alpine` | tidak dipublish | `pgdata_prod` → `/var/lib/postgresql` | `restart: always`, healthcheck `pg_isready` |
| `thc-vms-prod-minio-1` | `minio/minio:latest` ( overridable via `MINIO_IMAGE`) | tidak dipublish (internal `:9000` / `:9001`) | `miniodata_prod` → `/data` | `restart: always`, healthcheck `/minio/health/live` |
| `thc-vms-prod-migrate-1` | build `backend/Dockerfile` | - | - | one-shot, `restart: "no"`, wajib exit 0 sebelum backend start |
| `thc-vms-prod-backend-1` | build `backend/Dockerfile` | `8080:8080` | - | `restart: always`, healthcheck `wget /api/v1/health` |
| `thc-vms-prod-frontend-1` | build `frontend/Dockerfile` | internal `:3210` | - | `restart: always`, Next.js standalone |
| `thc-vms-prod-caddy-1` | `caddy:2-alpine` | `80:80` dan `443:443` | `./caddy/Caddyfile:ro`, `caddy_data` → `/data`, `caddy_config` → `/config` | `restart: always`, reverse proxy tunggal |

Batas sumber daya (`mem_limit` / `cpus`): postgres 1G/1.0, minio 512M/1.0,
migrate 256M/0.5, backend 512M/1.5 (`GOMEMLIMIT=450MiB`, `GOGC=75`), frontend
512M/1.0, caddy 256M/0.5.

Urutan start dijamin `depends_on`: postgres healthy → migrate exit 0 → backend
healthy → frontend start → caddy start. Port `8080` dipublish ke host khusus
agar `deploy.sh` bisa memanggil `/api/v1/ready` di `127.0.0.1:8080`; frontend,
database, dan object storage hanya hidup di jaringan compose. Nama service
storage adalah `minio`, jadi `S3_ENDPOINT=minio:9000` pada `.env` resolve
langsung ke service tersebut. Tag image diatur lewat `MINIO_IMAGE` di `.env`
(default `minio/minio:latest`); bila registry sedang bermasalah atau image
belum ada di cache VPS, pakai tag known-good
`minio/minio:RELEASE.2025-09-07T16-13-09Z`.

Bucket object storage tetap privat: `EnsureBucket` saat boot backend tidak
menerapkan policy publik dan tidak ada `mc anonymous`. Berkas dibaca lewat
endpoint backend `GET /api/v1/visits/{id}/file?kind=assignment_letter|id_card|selfie&visitor_id=<uuid>`
yang mengalirkan objek langsung dari object storage dengan scoping cabang,
sementara respons pembacaan kunjungan juga menyertakan tautan berumur pendek
(presigned, default `S3_PRESIGN_TTL_MINUTES=15`). URL absolut yang tersimpan di database tidak
pernah bisa diambil langsung. Caddy melayani `/s3/*` ke `minio:9000` dengan
prefix dipotong, sehingga `NEXT_PUBLIC_STORAGE_BASE_URL` dapat menunjuk origin
yang sama tanpa host S3 terpisah.

## 4. TLS & ACME (Caddy)

Alamat site Caddy diambil dari environment, bukan ditulis mati. Di
`caddy/Caddyfile` baris site address memakai `{$SITE_ADDRESS::80}`, yaitu
variabel env dengan nilai default `:80`. Service `caddy` meneruskan
`SITE_ADDRESS` dari `.env` VPS lewat key `environment` (default kosong), jadi
pindah domain cukup lewat `.env`, tanpa build ulang image.

- **Kosong (default)**: Caddy melayani catch-all di `:80` HTTP saja, aman untuk
  akses LAN via IP tanpa TLS. Ini kondisi VPS sekarang: diakses lewat IP LAN
  `10.11.6.110` tanpa IP publik, sehingga `SITE_ADDRESS` dibiarkan kosong.
  Verifikasi dulu di VPS sebelum yakin (daftar IP host dengan `ip -brief addr`,
  dan cek dari luar jaringan apakah ada IP publik yang terpetakan).
- **Diisi domain** (mis. `vms.thc.co.id`): Caddy menyajikan satu host dengan TLS
  otomatis (ACME) plus redirect HTTP → HTTPS. Syarat: DNS A/AAAA menunjuk IP
  publik VPS, port 80 dan 443 terbuka (firewall host + security group), dan
  nilai `SITE_ADDRESS` sama persis dengan domain tersebut. Tanpa IP publik,
  validasi HTTP-01 tidak akan lolos, jadi biarkan kosong sampai VPS punya IP
  publik.
- **Sertifikat persisten**: sertifikat ACME dan konfigurasi Caddy disimpan di
  volume named `caddy_data` (`/data`) dan `caddy_config` (`/config`). Kedua
  volume wajib ada: tanpa keduanya, tiap `up --build` meminta sertifikat baru
  dan bisa kena rate limit ACME. Jangan `docker volume rm` pada deploy.
- **Port 443**: mapping `443:443` memang ada di compose, tetapi selama
  `SITE_ADDRESS` kosong tidak ada listener di port tersebut. Tidak berbahaya.
- **Konsistensi env**: `SITE_ADDRESS` diisi di `.env` VPS (root repo); template
  `.env.prod.example` sudah menyediakan key `SITE_ADDRESS=` dengan default
  kosong. Isi `.env` tidak pernah di-commit. Bila `SITE_ADDRESS` diisi,
  samakan dengan `CORS_ALLOWED_ORIGINS` serta `NEXT_PUBLIC_API_BASE_URL` dan
  `NEXT_PUBLIC_STORAGE_BASE_URL`, karena nilai `NEXT_PUBLIC_*` dibakar saat
  build frontend: mengubahnya menuntut deploy (build ulang), bukan restart.
  Perubahan `SITE_ADDRESS` sendiri berlaku setelah deploy berikutnya, karena
  Compose membuat ulang container `caddy` saat konfigurasi environment-nya
  berubah.

## 5. Setup VPS Satu Kali

1. Install + daftarkan Gitea Actions runner di VPS (label `self-hosted, linux, vps`), user `vms` wajib di group `docker`.
2. `git clone https://git.thckalbar.com/thckalbar/vms.git /home/vms/thc-vms` (branch `main`).
3. `cp .env.prod.example .env`, isi SEMUA nilai `CHANGEME`: `POSTGRES_PASSWORD`, `MINIO_ROOT_USER/PASSWORD`, `DB_PASSWORD` (sama dengan postgres), `JWT_SECRET` (`openssl rand -hex 32`), `CORS_ALLOWED_ORIGINS` + `NEXT_PUBLIC_*` (domain publik), S3 produksi, dan `SITE_ADDRESS` (biarkan kosong bila akses via IP LAN, isi domain bila VPS sudah punya IP publik). `MINIO_IMAGE` boleh dibiarkan default.
4. Jalankan manual sekali: `./deploy/deploy.sh` — harus berakhir `DEPLOY OK`.
5. Caddy di dalam stack prod sudah berperan sebagai reverse proxy tunggal (host publish 80/443), jadi tidak perlu reverse proxy tambahan di depan. TLS/ACME dikonfigurasi lewat `SITE_ADDRESS` di `.env` (lihat §4). Port `8080` backend publish ke host hanya untuk healthcheck internal.

## 6. Operasi Rutin

- Deploy normal: cukup `git push origin main` dari Windows — sisanya otomatis.
- Cek status: `docker compose -f docker-compose.prod.yml ps` dan `curl -f http://127.0.0.1:8080/api/v1/ready`.
- Rollback: `git reset --hard <commit-lama> && docker compose -f docker-compose.prod.yml up -d --build` (migrasi bersifat maju saja — rollback kode tidak menurunkan skema).
- Jangan pernah jalankan seed ke production (`go run seeds/main.go` hanya lokal/QA).
- **Backfill notifikasi (one-off, idempotent)**: jalankan SEKALI setelah `migrate` perdana yang menambahkan tabel `notification` (migrasi 000008), atau kapan pun feed perlu diisi ulang dari riwayat kunjungan. Aman diulang berkali-kali:
  ```bash
  docker compose -f docker-compose.prod.yml run --rm --no-deps backend ./backfill-notifications
  ```
- **Interval worker**: `.env` `WORKER_INTERVAL` mengatur periode sweep auto-rule (default `15m`). Jaga nilainya `<= 45m` (`ReminderWindow`) agar reminder R4 tidak terlewat; nilai lebih besar memicu warning saat boot.
- **Cek container sisa**: sebelum dan sesudah deploy, jalankan `docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}'` (lihat §7).
- **Seed demo (one-off, manual)**: untuk VPS demo dengan DB kosong, jalankan SEKALI setelah stack naik. Binary `seeds` sudah tersedia di image backend, jadi cukup lewat compose (database host `postgres` hanya resolve di jaringan compose, bukan dari host):
  ```bash
  docker compose -f docker-compose.prod.yml run --rm --no-deps backend ./seeds
  ```
  Perintah ini mengisi master data + akun demo. Jalankan sebagai operator, tidak pernah otomatis oleh `deploy.sh`.
- **Tautan berkas**: bila memakai tautan presigned, pastikan `S3_ENDPOINT` dan `S3_PUBLIC_BASE_URL` di `.env` menunjuk host yang bisa dijangkau browser, bukan alias internal `minio:9000` saja.

## 7. Pembersihan Container Legacy

`deploy/deploy.sh` menjalankan blok pembersihan tepat sebelum
`compose up -d --build`. Tujuannya: stack lama (compose versi sebelumnya atau
compose dev) bisa masih jalan dan merebut port host, sehingga `up` gagal dengan
"port is already allocated" pada port 80, 8080, 3210, atau 5432.

Aturan keras yang berlaku (sudah diimplementasikan di `deploy/deploy.sh`):

1. **Hanya container yang dihapus.** Volume dan data tidak pernah dihapus oleh
   script. Penghapusan volume tetap keputusan operator secara eksplisit.
2. **Kandidat hanya container dengan label compose yang berbeda.** Label
   `com.docker.compose.project` dibaca untuk tiap container; kandidat adalah
   container yang punya label tersebut dan nilainya berbeda dari nama project
   produksi (`thc-vms-prod`, dibaca dari key `name:` di compose, dengan fallback
   `thc-vms-prod`). Container tanpa label compose sama sekali tidak disentuh.
3. **Kandidat harus terlihat milik stack THC-VMS.** Container dibuang hanya bila
   image-nya cocok pola `postgres:*`, `minio/*`, `rustfs/*`, `redis*`,
   `pgbouncer*`, `golang:*`, `node:*`, `caddy:*`, `nginx:*`, `thc-vms-*`, atau
   bila ia mem-publish port produksi (`:80`, `:8080`, `:3210`, `:5432`).
4. **Jumlahnya dicetak di log CI.** Setiap container yang dihapus dicetak
   beserta nama, image, dan project-nya, diikuti baris ringkasan
   `legacy containers removed: N`.

Konsekuensi yang perlu diketahui operator: container stack dev yang kebetulan
match image atau port produksi ikut terhapus (memang tidak boleh ada dua stack
yang berebut port yang sama di satu host). Pemeriksaan manual sebelum dan
sesudah deploy:

```bash
docker ps -a --format '{{.Names}}\t{{.Image}}\t{{.Status}}'
```

Jangan pernah menambah `docker volume rm`, `docker compose down -v`, atau
`docker system prune --volumes` ke dalam alur deploy.

## 8. Aturan Keras Deploy (ringkas; otoritatif di AGENTS.md §8)

1. Satu trigger saja (Actions). Webhook dilarang (port `9000` tabrakan dengan MinIO + risiko deploy ganda).
2. JANGAN deploy dengan `docker-compose.yml` dev; SELALU `docker-compose.prod.yml`.
3. JANGAN commit `.env` nyata dalam kondisi apa pun; root `/.env` sudah di-ignore.
4. `deploy.sh` wajib menolak bila `.env` hilang atau masih mengandung `CHANGEME`.
5. Bucket storage tetap privat; tidak ada `mc anonymous` / bucket public.
6. Tidak ada Redis/Kafka/microservices untuk MVP (background goroutine + pgxpool cukup).
7. Sertifikat ACME dan konfigurasi Caddy wajib persisten di volume `caddy_data` + `caddy_config`; jangan hapus volume saat deploy.
8. Pembersihan container legacy boleh menghapus container, TIDAK PERNAH volume atau data; penghapusan volume hanya atas instruksi operator eksplisit.
9. Seed hanya boleh dijalankan manual oleh operator (bootstrap demo), TIDAK PERNAH menjadi bagian dari alur `deploy.sh` atau workflow.
